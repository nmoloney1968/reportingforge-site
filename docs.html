What you will build in the Reporting Forge lab.

The lab is designed to take you from a single messy export to a small, repeatable workflow: a Python script that cleans your data, a Power BI report that visualises it, and a simple way to run the whole thing on a schedule.

End state: a small reporting stack you own

  • A Python script that pulls data from an export, API, or simple database.
  • Clear, reusable functions for cleaning, enriching, and validating that data.
  • A stable output file that Power BI can read without surprises.
  • A basic schedule - for example Windows Task Scheduler - so your report refreshes automatically.

Example flow

A typical workflow in the book might look like this: 

# 1. Pull data
fetch_export("usage_{{month}}.csv")        # from an SFTP drop or HTTP endpoint
load_reference_table("site_metadata.csv")  # local or shared drive

# 2. Clean and validate
df = load_usage()
df = normalise_columns(df)
df = apply_business_rules(df)
assert_no_negative_values(df, ["total_gb", "billable_gb"])

# 3. Enrich
df = join_site_metadata(df)
df = tag_alerts_for_thresholds(df)

# 4. Write outputs for reporting
write_parquet(df, "prepared/usage_{{month}}.parquet")
write_csv(df, "prepared/usage_{{month}}.csv")

# 5. Power BI points at /prepared and refreshes on schedule

Early chapters keep things even simpler and run everything manually from IDLE. As you progress you will introduce basic structure so your scripts stay readable and easy to change.

Configuration and structure

Instead of inventing a heavy configuration language, the lab encourages you to keep most logic in normal Python code. A light configuration file might exist just to describe sources and destinations in one place, while keeping actual rules in code: 

# monthly_usage.yaml (simple example)

name: monthly_usage_report

sources:
  - id: usage_export
    type: file.csv
    path: "inputs/usage_{{month}}.csv"

  - id: sites
    type: file.csv
    path: "inputs/site_metadata.csv"

outputs:
  - id: prepared_usage
    type: file.parquet
    path: "prepared/usage_{{month}}.parquet"

checks:
  - name: no_negative_values
    fields: ["total_gb", "billable_gb"]
    severity: error

The book walks through how to read this configuration from Python, run the checks, and produce outputs that downstream tools can rely on.

Where AI fits

Throughout the labs you will use an AI assistant to help with:

  • Drafting small functions or refactors.
  • Explaining error messages and suggesting fixes.
  • Thinking through edge cases and test ideas.

You still review and own every line of code. The aim is to move faster without giving up control of your reporting logic.

These docs will grow as the book and exercises solidify. Early readers will help refine the examples so they stay realistic and lightweight.

Environment concept

The book uses the idea of environments (for example dev and prod) mainly as a way to keep your experiments separate from anything that stakeholders see. In practice this can be as simple as different folders or different Windows user accounts.
