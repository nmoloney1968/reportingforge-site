How Reporting Forge workflows are expected to work.

These notes are intentionally early and high level. The idea is to provide a thin orchestration layer around the workflow you already write in Python, rather than a heavy new platform you need to learn.

A typical workflow looks like:

  1. Pull data from one or more sources - CSV exports, APIs, databases, or file drops.
  2. Run a set of checks and light transformations in Python.
  3. Hand the cleaned data to a template - PDF, slides, spreadsheet, or HTML.
  4. Render the output and ship it to destinations - email, S3, shared drives, or BI tools.
  5. Log the run, including inputs, versions, and any warnings.
Example pseudo workflow

In code terms you can think of it as something like:

fetch_usage() → validate_rows() → enrich_with_metadata() → render_template("client_monthly.pdf") → deliver(["email:client", "s3://bucket/path"])

Demo workflow (realistic pseudo-config)

A more realistic workflow might look something like this. The configuration is deliberately light so that most of the logic lives in normal Python modules, not in a separate DSL. 

# reportingforge-prod / workflows / monthly_usage.yaml

name: monthly_usage_report
schedule: "0 7 1 * *"   # 7am on the 1st of each month

sources:
  - id: starlink_usage
    type: s3.csv
    path: "s3://client-data/usage/{{ ds_prev_month }}.csv"

  - id: metadata
    type: postgres.query
    query: "SELECT site_id, region FROM sites WHERE active = true"

steps:
  - run: python:clean_usage.py
  - run: python:merge_metadata.py
  - run: python:validate.py

template:
  type: pdf
  file: templates/monthly_report.pdf.jinja

deliver:
  - email: "[email protected]"
  - s3: "s3://client-reports/monthly/{{ ds }}.pdf"
  - slack: "#reports"

In code, those steps map to simple Python functions stored in a predictable location: 

# clean_usage.py
import pandas as pd

def run(context):
    df = pd.read_csv(context["inputs"]["starlink_usage"])
    df["gb_used"] = df["bytes"] / 1_000_000_000
    df = df[df["gb_used"] > 0]  # remove zero rows
    context["state"]["clean_usage"] = df

Planned building blocks
  • • Workflow definitions in code-first configuration.
  • • Source connectors for files, databases, and APIs.
  • • Built in checks and simple assertions for sanity.
  • • Template rendering for PDFs, presentations, or HTML reports.
  • • Schedulers and triggers for recurring runs.
  • • Logging and run history for audits.
Environment concept

The landing page references an environment name: reportingforge-prod. In practice you might run multiple environments (dev, staging, prod) with the same workflows but different schedules and destinations.
